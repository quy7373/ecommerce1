## Boundaries and stack

React + Vite + Tailwind implements seven screens. Express is the only application gateway to PostgreSQL through Prisma. Google provides identity; the API issues its own JWT session. Stripe Checkout handles test card entry. A server-side support service retrieves approved internal documents before calling a configured AI provider. The browser never receives database, OAuth client, Stripe secret, or AI credentials.

A modular monolith keeps catalog, cart, checkout, orders, administration and identity in one backend. The public support route delegates to an isolated support runtime without commerce/session/payment credentials; a module sharing the API's secrets is insufficient. A separate worker process from the same backend package reconciles payments and expired reservations using PostgreSQL as durable work storage. No Redis, vector database, or message broker is required for this scope. Parameterized keyword retrieval over approved document chunks is adequate initially; replace retrieval behind the same interface if evaluation warrants embeddings.

## Identity and authorization

Google authorization-code flow uses server-held, single-use state, nonce, and PKCE verifier with a five-minute expiry. Bind state to an HttpOnly transient browser cookie. Exchange the code on the server using the exact configured redirect URI. Verify Google signature, issuer, audience, expiration, nonce, subject, and verified email. Identify users by Google's stable subject; never silently link accounts by email. New accounts receive CUSTOMER. Bootstrap ADMIN through an operator-controlled process, never a registration field.

Issue a 15-minute ES256 JWT in production __Host-session cookie: Secure, HttpOnly, SameSite=Lax, Path=/, no Domain. OAuth binding uses __Host-oauth with the same attributes and five-minute lifetime; loopback HTTP development uses separate names only. Claims: sub=user UUID, sid=AuthSession UUID, iss=configured API issuer, aud=configured application audience, iat, exp. Pin the algorithm/keys and validate all claims. A database session allows immediate logout; resolve the current user role from the database on every authorized request. Admin routes additionally require proven MFA assurance; mutations require authentication <=5min old via the approved assurance mechanism. No refresh token in MVP; expired users sign in again. Browser requests use credentials and a per-session CSRF header on mutations. Enforce exact Origin allowlists and CORS credentials; never use wildcard origins. OAuth redirects and Stripe redirects come from server configuration, not user input. See the security authentication document for the open MFA integration gate; ordinary Google login is not MFA proof.

Google validation reference: [OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect).

## Prices and reservation workflow

Single currency USD for the test implementation; all money is integer cents. Zero shipping and zero tax are demo calculation defaults requiring owner approval before commercial use. No discounts, multi-currency, tax engine, guest checkout, or automated refunds in MVP. Cart values are estimates; order creation re-reads prices and active status. Order item name, SKU, price, and shipping address are immutable snapshots. At most one pending order per cart version; reservation does not remove cart items until payment succeeds, and only purchased quantities still matching the captured cart version are removed.

Within a short SERIALIZABLE transaction, lock products in sorted ID order, verify available=stockOnHand-stockReserved, increase stockReserved, snapshot the order, and create ACTIVE reservations. Retry the complete transaction on serialization/deadlock errors with bounded backoff (maximum three attempts); then return 503. Add SQL CHECK constraints for 0 <= stockReserved <= stockOnHand and all money/quantity bounds. Prisma migrations must include constraints that its schema cannot express. Never call Stripe while holding database locks. [PostgreSQL isolation guidance](https://www.postgresql.org/docs/current/transaction-iso.html) requires retrying aborted serialization transactions.

The order initially holds inventory for30min (technical demo default). Create Checkout using deterministic provider idempotency key checkout:<orderId>:1 and orderId metadata. Freeze checkoutRequestedExpiresAt=firstAttemptAt+31min before the first call (one-minute margin over Stripe's minimum session duration); retry with identical provider parameters, never recompute expiry. Persist the session ID and actual provider expiry, extending ACTIVE reservation timestamps atomically if needed before exposing the session. If frozen parameters are no longer valid for new creation and the original outcome is unknown, reconcile/review instead of changing keys/parameters blindly. Do not release inventory merely because the local timer elapsed: the worker must retrieve/expire the provider session and resolve whether it was paid. Unknown network outcomes leave reservations held and retryable. An order with no recorded session is reconciled with the same provider key before cancellation/release, because creation might have succeeded remotely. Unstarted orders may be released after the worker claims them and prevents future session creation atomically. After24h unresolved creation enters PAYMENT_REVIEW; never blindly reuse a potentially pruned provider key. Enforce max3 pending orders/user transactionally to limit stock hoarding.

## Payment and cancellation consistency

Restrict Checkout to immediate card payments in test mode. Register the Stripe route with raw-body middleware before JSON middleware. Verify Stripe-Signature with the endpoint secret and SDK timestamp tolerance before parsing business fields. Reject live-mode events in the test deployment. Validate the session's order reference, provider session ID, amount_total, currency, mode, and payment_status against the database. A success redirect never marks an order paid.

Persist verified events in WebhookEvent with unique provider event ID before returning 200; a worker retries processing. In a single transaction, claim the event, lock the order and its reservations, make an allowed transition once, consume reserved stock (decrement onHand and reserved), record payment, and mark the event processed. Duplicate event IDs or different events for the same paid session do not repeat stock changes. Unknown relevant orders and mismatches enter reconciliation with redacted alerts; never acknowledge without durable storage. A storage outage returns 503 so Stripe retries. Older failure/expiry events cannot overwrite PAID. Fulfillment starts only after payment confirmation.

Customer cancellation is limited to PENDING_PAYMENT. Mark cancellationRequestedAt atomically to block new session creation, then expire/retrieve the session outside the transaction. If payment won, settle PAID and return 409; otherwise transition CANCELLED and release ACTIVE reservations once. Pending provider calls return 202 and worker reconciliation continues. PAID cancellation/refund requires a future approved policy and is unsupported by this API. A contradictory late paid event after a terminal release enters PAYMENT_REVIEW; do not fulfill or decrement unreserved inventory. Operator resolution/refunds occur in Stripe test dashboard and require audit; no automated recovery API in MVP.

References: [Stripe webhook handling](https://docs.stripe.com/webhooks), [Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment), [idempotent requests](https://docs.stripe.com/api/idempotent_requests), [Checkout expiry constraints](https://docs.stripe.com/api/checkout/sessions/create.md).

## Support privacy and trust

Only documents explicitly marked APPROVED with owner, version, and approval date are indexed. All supplied policy files are DRAFT and excluded. Without approved relevant evidence return an escalation message with no policy assertions. Treat user text and retrieved passages as untrusted data; instructions within them cannot change system rules. No tools for payment, refunds, orders, or database access are exposed to the model. Support is public and FAQ-only; authenticated users receive the same document corpus.

Strip apparent emails, phone/address information, payment details, tokens, and order identifiers before sending a maximum 2,000-character message to a provider. Redaction is best effort: UI asks users not to supply personal information, and external AI use must remain disabled until an owner approves the provider, processing terms, and retention. Store no chat transcript by default; keep redacted aggregate latency/outcome metrics only. Check every citation against retrieved approved chunk IDs; discard unsupported answers. Prompt filtering alone is insufficient; use retrieval and output checks plus adversarial evaluation. Provider failure returns 503; no evidence returns a safe 200 escalation response.

## Operations

Docker Compose services: frontend, api, worker, isolated support, postgres, audit collector, and a one-shot migration service. Production additionally needs approved managed secret/KMS, immutable audit storage and isolated encrypted backups. PostgreSQL is internal-only with an encrypted persistent volume and verified TLS; API and worker wait for successful migrations and DB health. Use distinct least-privilege roles; worker cannot decrypt addresses, support can read approved public corpus only, migration credentials never enter runtime containers. Shared ingress/DB-backed rate limits must work across replicas. Frontend serves built assets and proxies /api to Express for same-origin cookies. Vite development uses the same proxy. Stripe/Google/AI remain external and need network access; never represent them as local containers. Use an explicitly pinned supported dependency set chosen by implementers and commit lockfiles. CI runs unit/integration/E2E and security checks before release; migrations run once, not per replica.

Separate readiness (database access) from liveness, use request IDs, redact cookies/addresses/provider payloads in logs, enforce request size limits, rate limits and timeouts, and retain payment audit identifiers with restricted access. Backup/restore verification, TLS, secrets management, policy approval, monitoring and reconciliation runbooks are release gates. Retention periods, shipping countries, tax treatment and return/refund promises require owner decisions.
