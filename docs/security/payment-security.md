# Payment and inventory security

Task SEC-001. SEC-08/09/12/14; threats T-05/06/12/16. Stripe Checkout is hosted and test-mode only. Never build a local card form, proxy card payloads through Express, log card inputs or store PAN/CVV. Hosted Checkout reduces application exposure; it does not by itself determine merchant PCI scope or prove compliance. Owner/acquirer review is required before any live payment deployment.

## Session creation and data minimization

Require current session, owned PENDING_PAYMENT order, no cancellation intent, validated reservation and Idempotency-Key. Enforce per-user pending-order/session quotas from [API security](api-security.md), transactionally under a user/order lock so parallel requests cannot bypass them. Use immutable server order lines, integer amounts and USD; reject client price/status/currency/userId. Do not pass shipping address, phone or Google email to Stripe unless a future documented processing purpose requires it; current Checkout metadata contains orderId only. Order/payment IDs remain sensitive references even when no card data is retained.

Server supplies fixed allowlisted success/cancel locations; response checkoutUrl must be HTTPS checkout.stripe.com without credentials or nonstandard port. No user returnTo URL. Test key and webhook secret are separate values from secret manager, never VITE_ configuration. Production startup rejects live keys under this release's test configuration and startup logs show no key fragments. Pin Stripe SDK/API snapshot event version, test contract changes before upgrades and disable automatic payment methods outside the card-only allowlist.

Claim creation in the database, then call Stripe outside SQL locks using deterministic key checkout:<orderId>:1 and immutable stored parameters. Store/freeze Order.checkoutRequestedExpiresAt on first attempt; a retry must not recompute it because Stripe rejects different parameters for the same key. The exact proposed storage field is in the updated dictionary. Request expiry >=provider minimum30min from creation with an operational margin (proposed31min from first attempt), rather than an order timestamp that is already old. Align ACTIVE reservations to actual provider expiry before exposing URL. If the original request did not create a session and its frozen expiry is now invalid for new creation, do not change parameters or key blindly: reconcile/enter review and confirm the remote outcome before any replacement order.

Provider idempotency is not permanent business deduplication. One local order has at most one session; after an unknown creation outcome, recover the same session/key within its retention window. After24h without a provable outcome, enter PAYMENT_REVIEW, retain active holds and alert; never create a new session under a potentially pruned provider key. Repeat browser submits reuse the application key for the same logical operation. No network timeout is evidence of failure or payment success.

## Webhook security and durable processing

1. Read a bounded raw application/json body before JSON parsing. Verify Stripe-Signature using the maintained SDK, endpoint-specific secret and300s timestamp tolerance; keep host clocks synchronized within30s and alert on drift. Never disable recency checks. During rotation accept only explicit current/previous endpoint secrets for a bounded overlap, proposed<=24h, then remove the old one. A retry legitimately has a new delivery signature; event ID deduplication is still necessary.
2. Reject invalid/missing signature/malformed envelope with400; reject live-mode event in test with400 WRONG_PAYMENT_MODE. Do not trust source IP alone or a user/admin cookie. Unsupported signed event types are safe no-ops after durable recording; only allowlisted event handlers execute business logic.
3. Store unique provider event ID and minimal verified projection before200. Storage outage returns503. Do not synchronously acknowledge an event stored only in process memory. Never persist the full customer_details/card-bearing provider payload. Redact failed bodies and signature headers in ingress/APM logs.
4. Worker claims a durable event with recoverable lease, validates provider account/environment and session type/mode/payment_status, exact session/order binding, amount_total, currency and metadata against immutable local order. If webhook arrived before session persistence, reconcile the in-flight order/provider creation; do not attach a random session solely because metadata has a matching UUID. On uncertain state retrieve current session through the same pinned Stripe account.
5. Lock order/reservations/products in consistent order. Atomically record a unique Payment, transition status, consume ACTIVE reservations and mark event processed. Unique event ID, unique order/session payment and status-aware conditional updates cover different event IDs representing the same payment. If state is already paid, do not consume stock again.
6. Reordered failure/expiry cannot regress paid/fulfillment states. A contradictory paid event after release or amount/session mismatch is a review event, not permission to fulfill. Correctly signed semantic mismatches remain durable and acknowledged but generate restricted alerts. Unprocessed/review events remain visible to operators.

References: [Stripe signature and raw-body guidance](https://docs.stripe.com/webhooks), [fulfillment and concurrent retries](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page), [provider idempotency](https://docs.stripe.com/api/idempotent_requests), [session expiration parameters](https://docs.stripe.com/api/checkout/sessions/create.md).

## Inventory and cancellation

Use SERIALIZABLE transactions with bounded complete retries, sorted product locks and CHECK constraints 0<=reserved<=onHand. Reserve at order creation, not cart edit. Consume reduces onHand/reserved once; release reduces reserved once. Admin stock updates lock the same rows and reject a value below reserved. No external provider call occurs inside a lock-holding transaction.

Cancellation first records intent and blocks new creation, then confirms provider unpaid/expired outside SQL locks. If payment won, settle paid; if outcome is unknown return202 and retain stock. Local expiry alone cannot release inventory. Unstarted orders can be closed atomically before a session starts. Reconciliation retries state transitions after lease expiry/crash safely; three active pending orders per user limits simple stock hoarding but not distributed abuse. Expiry extensions occur only during the initial provider session alignment, never on user polling/retries.

PAID->PROCESSING->SHIPPED requires admin authority, recent authentication/MFA and audit. No API manually marks paid or performs refunds in MVP. Review cases/manual Stripe test actions require authorized two-person operator review and recorded provider references; no SQL shortcut bypasses inventory invariants. Operator edits do not erase original events. PCI applicability, fraud controls, commercial refunds and live payment rollout remain separate release decisions.

Required tests: authentic/tampered/stale signatures; test/live mismatch; raw-body middleware order; duplicate delivery and distinct events for one session; forged redirect; metadata/amount/currency/session mismatch; interrupted create/record/settle; concurrent pay/cancel/expire/admin-stock writes; key retries with identical provider parameters; provider outage and clock skew. Inspect DB/logs/browser reports for forbidden card data. Passing these tests reduces risk but leaves provider compromise, fraud, bot hoarding and operational review delays as residual risks.
